## 이 작업이 실제로 잡아낸 것

E2E는 "테스트가 초록인데 화면이 깨져 있던" 문제를 겨냥해 만들었고, 실제로 **jsdom이 구조적으로
볼 수 없는 것 3건**을 잡았다. 이게 이 스위트의 존재 이유다.

1. **상단 툴바가 이미 프로덕션에서 두 줄이다.** `.top-toolbar`가 `flex-wrap: wrap`
   (`globals.css:1100`)인데 `.detail-page` 내부폭이 704px라 버튼 17개가 안 들어가 실행취소·
   다시실행이 내려간다. **520개 테스트 중 무엇도 볼 수 없었다**(jsdom은 flex를 계산하지 않는다).
   → 레이아웃은 미수정 결정. 오늘을 기준선 삼아 테스트를 정직하게 개명하고
   (`"상단 툴바가 두 줄을 넘지 않는다"`), 줄바꿈은 `docs/BACKLOG.md`에 UX 개선 후보로 분리.
2. **CI 실패 진단 아티팩트가 0바이트였다.** 실패 시 `playwright-report/`를 업로드하는데
   CI reporter가 `line`이라 디스크에 아무것도 쓰지 않았다. **CI가 초록이라 영영 안 드러났을
   결함**(실패 경로는 실패해야 드러난다). → `reporter: [["line"], ["html", {open:"never"}]]`.
3. **"2겹 프로덕션 차단"이 사실은 1겹이었다.** 빌드·런타임 두 게이트가 같은
   `NEXT_PUBLIC_E2E`에 걸려 있었고, 그 변수는 **빌드 타임에 인라인**된다 → 플래그를 켠
   빌드에서 런타임 가드는 `if ("1" !== "1")`, 죽은 코드. 주석은 하필 자기가 못 막는 경우를
   막는다고 적혀 있었다. → `NODE_ENV`라는 독립 입력을 추가해 주장을 참으로 만들었다.

## 알아 둘 것

- **E2E는 dev 서버(`npm run dev`, Turbopack) 대상으로만 돈다.** 하니스가 프로덕션 빌드에
  존재할 수 없으니 이건 설계상 강제된 결과지만, **이 스모크들이 프로덕션 렌더 경로를 덮는다고
  가정하면 안 된다.**
- `NODE_ENV` 가드 때문에 `next build && next start` 대상 E2E는 불가능하다(의도된 대가).
- `retries: 0`은 정책이다. flaky를 재시도로 덮으면 "CI 빨간불 = 진짜 신호"가 다시 깨진다.
- 하니스의 `.detail-breadcrumb`·`.detail-cover`는 정적 대역이라 원본이 바뀌어도 안 따라간다.
  `harness.spec.ts`의 그 두 단언은 제품 커버리지가 아니라 드리프트 가드다.

## 검증 규칙 (누적)

> **1. 모든 팝오버·메뉴·드롭다운은 "열기 → 항목 클릭 → 닫기"까지 실제로 조작해 확인한다.**
> 렌더 확인 ≠ 동작 확인. (2026-07-23)

> **2. 에디터 시각 회귀는 직렬화(`getHTML()`)가 아니라 렌더된 DOM(`editor.view.dom`)으로
> 검증한다.** nodeView를 타는 노드는 두 경로의 출력이 다르다. (2026-07-27, DESIGN.md §2.15)

> **3. 검증 스크립트에는 대조군을 함께 돌린다.** "0건 발견"은 스캔이 실제로 뭔가를 읽었을
> 때만 의미가 있다. 이번에 프로덕션 마커 스캔이 청크를 하나도 못 받은 채 "마커 0건"을
> 보고했다(원인: `while read` 루프 안의 `curl`이 stdin을 먹음 → `</dev/null` 필요).
> 대조군이 없었으면 공허한 초록을 그대로 믿을 뻔했다. (2026-07-30)

> **4. 변화를 기다리는 검사는 "변화가 일어날 수 있는가"부터 확인한다.** 배포 감지를 청크
> 해시 변화로 하려 했으나, 이 브랜치는 프로덕션 번들을 바꾸지 않아 해시가 원리상 불변이었다
> — 영원히 발화하지 않는 감시였다. 발화 조건이 성립 가능한지 먼저 따질 것. (2026-07-30)
